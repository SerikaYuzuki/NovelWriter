# 原稿保全とAI拡張の確認結果（2026-09-26）

この文書はgrill-me対話の合意と、現行コード・運用の確認結果を分けて記録する。機能の実装完了を意味しない。

## 優先順位

自分がMac・iPhone・iPadで安心して書き続けられることを成功条件とする。一般公開・収益化・Windows対応には期限を設けない。Apple版を希望する人への個別試用は妨げない。AI拡張も自分の執筆用途として検討する。

## 原稿保全の合意

- 同期を明示的に有効にした作品全体を保護する。未同期作品を勝手に送信しない。
- 追加費用は原則なし。自宅サーバーを使用し、外部バックアップは要求しない。サーバー全損でそこにしかないデータが失われることは許容する。
- 正常なオンライン時、ローカル保存済みの変更を1分以内にサーバーへ送ることを目標にする。オフライン中の未退避分の損失は許容する。
- 直近7日間は同期された各時点、それより古い分は日単位で1年間戻れるようにする。
- 通常の作品削除は一覧から隠す操作へ変更し、削除日から1年間、復元用データを保持する。
- 復元は現在の作品を上書きせず別作品として取り出す。専用画面は必須でなく、手順書や支援を使って当日中に戻せればよい。
- 未同期の変更が5分以上残ったら、小さなアプリ内表示で知らせる。執筆を遮る通知にしない。
- アカウント削除の30日取消猶予は維持する。通常の作品削除の復元とは別に扱う。
- 他ツールへの移行では本文と資料が読めればよく、構成の完全再現は要求しない。

保持方式の推奨は、既存の同期graphを直ちに間引く方式ではなく、復元用の作品アーカイブを作る方式。前者はwire互換・cold import・親参照・競合根の再設計が必要である。後者は保存容量を別途見積もる必要があるが、現行v2の整合性を維持しやすい。保存量を減らすGCまで実装済みとはしない。

## 現行バックアップの実確認

2026-09-26、自宅サーバーの既存運用設定を用いて確認した。原稿・鍵・認証情報は出力していない。

- 最新成功記録: `2026-09-26T02:17:04.309352+00:00`（日本時間11:17）。cron登録も確認。
- 最新backupの作成: `2026-09-26T02:17:02.004579+00:00`、期限: `2027-09-26T02:17:02.004579+00:00`。manifestを持つ保存セットは18個。
- database／secrets／configurationの3暗号化ファイルを認証検証し、成功。
- 最新databaseを同じPostgreSQLコンテナ内の新規・隔離DBへ`pg_restore --exit-on-error --no-owner --no-privileges`で復元し、成功。sync_v2の24 tableを確認。復元区間は約1.75秒。
- backup用migrator roleにはDB作成権限がなく、初回のDB作成は失敗した。DB作成可能な既存管理roleを確認して再実行した。新規DBは検証後に削除し、稼働DBは変更していない。
- objectの実体は`sync_v2.global_blobs.raw_bytes`に格納される設計で、DB dumpの対象。ただし今回は個々の作品の意味的な内容照合・アプリ読込までは実施していない。

この検証は暗号化ファイルとDB全体の復元可能性についての証拠であり、鍵を再配置した新サーバー起動、作品単位の別作品復元、Apple端末の受入、当日中の一連の復旧手順の完了証拠ではない。`--no-owner --no-privileges`を使用しているためrole／権限再現の検証でもない。

## 原稿保全の実装時の受入

1. 合成作品を各Apple端末で保存し、サーバーの受領世代まで測る。本文更新は正常系60秒以内。競合・大きな添付・背景移行は別シナリオで結果を記録する。
2. サーバーだけを一時的に利用不能にし、ローカル保存が成功すること、5分で小さな表示が出ること、サーバー回復後に未送信分が再開することを確認する。
3. fixture時刻で7日境界・1暦年境界を検証する。継続して残る復元点のmanifest/objectが欠落しないこと、期限切れの整理が他作品へ波及しないことを確認する。
4. 作成直後の削除、複数端末からの削除、旧クライアントの再送を含め、通常一覧から消えても削除時の最終内容を新IDで復元できることを確認する。account削除を迂回して再公開しない。
5. 本文・プロット・人物・添付を含む合成作品を別作品へ復元し、元作品が変わらないことを確認する。手順書で一連の復旧時間を計測する。

推奨構成は、AIチャットとMCPを別々のDB編集機能にせず、共通の作品編集サービスへ接続する方式。NovelCoreは依存ゼロのまま、アプリ側でwork/session/account、IME、世代、Undoとローカルcheckpointを管理する。MCPからSQLiteファイルや稼働エディタ本文を直接書き換えない。MCPはMacでアプリが起動している間だけ提供し、サーバー常駐型は今回の対象外とする。

### AIについて採択した方針

- 共通の基本プロンプトと作品ごとの追加指示を両方同期する。作品固有の指定を優先する。次回送信には最新の指示を使い、過去の送信には当時の実効プロンプトを記録する。
- チャット履歴は作品と一緒に同期し、Mac・iPhone・iPadで会話を継続する。
- 会話開始時にその作品全体の参照を許可する。同じ会話では送信ごとの確認を繰り返さず、別作品は参照しない。全体の参照許可は毎回の全文送信を要求するものではない。
- 編集許可は参照許可と分け、依頼ごとに対象範囲を指定する。指定範囲内では本文も含め直接編集し、個々の変更案の採用確認は必須にしない。依頼完了時に編集許可は失効する。
- AIの処理中も執筆できる。同じ箇所を利用者が変更した場合はAIの反映を止め、生成結果をチャットに残す。無関係な箇所の編集だけで一律に失効させない。IME・work/session/accountの整合性は維持する。
- 続きの生成は、指定した話の末尾への追記から始める。既存本文の書換えは別に範囲を指定した場合だけ行う。追記は一度のUndoで戻せるようにする。
- アプリ終了後のAI処理継続は保証しない。再開時に中断を表示し、自動再送しない。保存済みの会話・変更は残す。
- MCPはMacでFUMINIWAを開いている間だけ利用できればよい。本文、章・話の構成、プロット、人物、伏線、メモ、資料の読み書き・追加・並べ替え・削除を対象にする。作品そのものの削除、アカウント・APIキーの管理は公開しない。
- MCPでも外部AIへの依頼で指定した対象範囲を許可として扱い、FUMINIWAで同じ確認を繰り返さない。範囲外の操作は拒否し、変更はアプリで確認・取り消し可能にする。

### 実装で詰める契約

製品方針と区別する。以下の未確定部分を、実装済み・検証済みとして扱わない。

1. 共通プロンプト用のaccount単位の同期契約、作品別指示の保存形式、端末別の既存設定からの移行。APIキーは端末限定のまま分離する。
2. 会話・message・依頼・適用結果のIDと永続化。二端末から同時送信した場合も発言を消さず、実行中の依頼を他端末が自動で引き継がない。複数会話の画面構成は未確定。
3. MCP接続の認証と、依頼範囲をアプリが検証できる許可情報への変換。モデル自身が送る「許可済み」という主張だけを認可に使わない。接続する外部AIがどのように依頼範囲を伝えられるかを確認し、追加確認を避けられない制約があれば判断点として提示する。
4. 本文範囲／構造化項目単位の比較、依存する削除・並べ替えも含む競合検知、Undoの単位。操作IDによる重複適用防止とcheckpoint完了後の結果記録を揃える。
5. アプリ終了・通信切断の状態遷移。提供元の処理が続く可能性とローカルの中断を区別し、不明な結果を自動で再送・再適用しない。
6. 長い会話と作品の入力上限、必要部分の取得方法。履歴の省略や要約をする場合にも、同期保存した元の会話は保持する。

受入では、合成作品で端末間の会話継続、実効プロンプト履歴、範囲外操作の拒否、同じ箇所／別の箇所の同時編集、IME、Undo、終了後の中断表示、MCPの重複呼出しを確認する。私的原稿や実APIキーを開発テストへ送信しない。

現時点ではAI提供元の追加や料金変更は選定していない。既存のAPI送信実装は再利用候補だが、各提供元の会話・tool呼出しの最新仕様確認は方式決定後に行う。

## 次の実装単位

推奨順は、(1) 削除保管・別作品復元と復元手順、(2) 同期再試行・遅延表示、(3) AI共通編集サービスとプロンプト／会話同期、(4) チャット・生成編集、(5) 同じ編集サービスを使うMCP。履歴アーカイブとGCの詳細は(1)で契約として確定する。指定範囲内での直接編集を基準とし、範囲の付与・撤回と競合拒否を(3)に含める。

今回の検証はコード読取と運用バックアップの隔離復元。アプリコード・serverコード・schemaの変更、実機受入、公開反映は未実施。
