# 原稿保全の実装設計

状態: Opus 5.5による方針の再レビューPASSを受けて開始した設計。未実装。新APIの正確なschema・fixture・migration番号は実装時に現行inventoryを確認して追加する。既存migrationを編集しない。

## 1. 今回の境界

端末SQLiteを正本とし、現行Snapshot Sync v2を維持する。対象は明示的に同期した作品。外部バックアップ、未削除作品のgraph GC、Windows、公開・販売は対象外。変更単位はserver保管、別作品復元、端末の削除状態表示、再試行・遅延表示に分ける。

AIは本文snapshotと別の同期経路を使うため、この設計でAI entityをsnapshotへ追加しない。後続AIのtableもaccount削除と作品保管に参加できるよう、削除境界を共通化する。

## 2. 同期済み作品の削除と保管

- 現行の`deleted_works`による同じWorkIDの再利用禁止を維持する。削除済み作品のgraphを即座に消す処理を、保管への状態遷移と期限後purgeへ分離する。
- 削除要求をaccount lockと作品lockの同じtransactionで直列化する。初回削除日時と1暦年後の期限を固定する。再送で期限を延長しない。2月29日の翌年期限は2月28日、時刻はUTCで保持する。
- 初回のDELETE成功前に、サーバー受領済みのhead・履歴・object参照が保管対象になっていることを保証する。保管に失敗したら削除を成功扱いしない。
- 保管中もworks/snapshots/objectの参照整合性を維持する。通常のcatalog、head、history、object取得からは除外し、既存の全commandで再publish・clone元／先への利用を拒否する。保管専用の復元経路だけにアクセスを許す。
- 未知のWorkIDの削除も同じ冪等応答とし、他accountの存在を漏らさない。旧clientのDELETEも新serverで保管する。旧clientの画面に残る「不可逆」の表現はclient更新で修正する。
- 新clientは最後の未送信checkpointを保持してから削除を開始する。保管したサーバー内容と未送信の端末内容を混同しない。送信を完了できない場合、端末内容を消さず救出可能な状態で残す。日次backupの時刻には依存しない。
- 期限後purgeはaccount lock下で再判定し、小さなbatchで行う。旧graph削除の参照順序を再利用し、他作品と共有するobjectは残す。再送拒否用tombstoneは残す。

## 3. アカウント削除と他端末

- account削除確定は作品保管期限より優先する。保管graph、復元receipt、後続のAI同期tableも稼働DBから消す。共有objectは他accountの参照を維持する。
- `account_deletion.rs`の列挙削除と`account_deletion_gate`を同時に更新する。日次backupは既存の保持と復旧時の再公開禁止を維持する。
- 新clientが区別できる作品削除状態を契約に追加する。generic 404だけで削除と判断しない。認証されたaccount内でのみ状態を返し、旧clientの互換応答と新clientの利用開始条件をschema・fixtureに定義する。
- 別端末に編集が残る場合、現在の本文を消さず「別端末で削除済み」と表示する。「新しい作品として残す」は新WorkID/DocumentIDへ明示的にコピーする。削除された旧IDへ再送しない。
- accountが異なる場合に救出データを勝手に送信しない。ローカル救出と新作品の同期有効化を分ける。

## 4. 別作品としての復元

- 既存の同一WorkIDへのrestoreは変更せず、保全用の「別作品へ取り出す」を別操作として追加する。初期版は手順書と専用の操作ツールでよく、専用画面は必須ではない。
- 認証scope、元WorkID、選択snapshot、復元操作ID、新WorkID/DocumentIDを固定する。再実行は同じ操作IDの結果を読み返し、二重作品を作らない。
- サーバーで選択manifestと必要objectが全て存在することを検証する。新IDを使った新rootを正規のcanonicalization/hashで生成し、旧作品へのparentリンクを持たせない。章・話の順序と内部参照、本文・人物・プロット・メモ・添付を保つ。
- serverへ新作品を作る場合は、scope再検証・保管期限確認・新root/head作成・receiptを同じtransactionにする。削除期限・account削除と競合した場合は安全に失敗させる。
- 後続AIデータの複製は実行権限を継承しない。本文の選択時点と会話の取得時点を別記録とし、チャットが同一時点の復元であるとは表示しない。AIデータ込みの復元はその永続化契約完成後に受入を追加する。
- 操作後はアプリで別作品を開き、合成fixtureの全内容を照合する。DB全体の復元成功だけではこの受入を完了にしない。

## 5. 履歴の扱い

未削除作品の既存graphは保持する。直近7日間は受領済みsnapshotを列挙し、古い部分は日本時間の日付ごとの最後の受領時点を選択できるようにする。編集のない日は架空の復元点を作らない。1年を最低復元期間として扱い、それ以前のgraphを新たに削除しない。削除保管は削除日から1年でpurgeする。

履歴表示の圧縮と物理的な容量削減を区別する。容量見積もりとGCは別の設計変更であり、この段階で二重の日次作品アーカイブを導入しない。

## 6. 送信再試行と小さな遅延表示

- 正常時はローカルcheckpoint成功からworkerを起動する。1分目標の起点は保存済み世代、終点はその変更を含むサーバー受領確認。連続入力中・IME中の未保存分まで保証を広げない。
- 一時的失敗には作品ごとの単一retry taskを設ける。初回2秒、指数backoffとjitter、最大60秒。新しい保存・接続回復・前面復帰で早く再開できる。wakeの重複で二重workerを作らない。
- 認証不成立・account不一致・競合・隔離・削除済みは自動解決しない。終了・scope変更でtimerを止めるがdurable outboxは残す。再起動で未送信laneから再開する。
- 未受領変更の最古時刻と世代を端末に保持する。新しい編集で古い未受領時刻をリセットしない。受領確認と対象世代の照合後にだけ解消する。
- 5分を超えたら作品一覧と現在の作品の既存ステータス領域へ小さく表示する。通知ダイアログ・音・執筆停止は不要。競合・認証・隔離など理由に応じた文言を使う。
- 実行中は単調時刻、再起動後は永続化した時刻を用いる。時計が逆行した場合は「時刻不明の未同期」として扱い、同期済みと偽らない。
- iOS停止中と大きな添付の送信時間は正常系本文更新の60秒受入から分ける。背景移行ではローカル保存を優先し、前面復帰で再開する。

## 7. 実装順と検証

1. serverの保管・purge・account削除と互換契約。共有object、再送、期限、旧client、scope違い、account削除との競合をPostgreSQL fixtureで確認。
2. 別作品復元と手順書。操作ID再送・graph欠落・元作品不変・添付・内部参照・削除期限競合を合成作品で確認。
3. clientの削除伝播と救出。未送信のまま削除、別端末削除後のoffline編集、account切替、IME、再起動を確認。
4. retryと小さな表示。fake clock、serverだけ停止→回復、受領喪失、世代の追越し、時計逆行、複数作品を確認。
5. 保存・互換・共有基盤の変更なので`./Scripts/check.sh`と対象buildを実施。Mac/iPhone/iPadの実機で正常時遅延と復元操作を確認。必要なserver反映はbackup・migration・反映後確認を伴う別の実施段階として記録。
