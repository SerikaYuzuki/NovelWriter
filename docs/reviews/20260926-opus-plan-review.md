## High（AI系の設計を止める）

**F1. 会話・作品別指示を作品に含めて同期すると、現行の同期の仕組みでは「発言を消さない」を満たせない**
- 根拠:
  - 競合時の選択肢は「この端末」「サーバー」「両方残す」の3つだけで、作品全体単位です。自動マージはありません（`NovelKit/Sources/NovelSyncV2Application/ConflictTypes.swift:4-8`）。
  - 作品に入れられるデータの種類は固定で、知らない種類は拒否されます（`NovelKit/Sources/NovelSyncV2/SnapshotValidation+Entity.swift:15-33`、server側 `SyncServerV2/src/application.rs:236`〜）。
  - 保存済みの感想・アドバイスは添付ファイルとして作品に入れて同期しています（`NovelApp/Features/AssistantFeedback/AppState+AssistantFeedback.swift:16-25`）。
- 矛盾する箇所: 計画の73行目・87行目。たとえば「iPadでチャットしながらMacで執筆」すると作品全体の競合になります。「この端末」か「サーバー」を選べば片方の発言が消え、「両方残す」を選べば作品が2つに分かれます。新しいデータ種類を足すと、旧クライアントがそのスナップショットを拒否します。
- 修正案: 共通プロンプト・作品別指示・会話を、スナップショットとは別の「AI用データの同期経路」にまとめることを推奨します。
  - アカウントと作品IDで区切り、発言は追記専用にして message ID で重複を防ぎます。
  - 指示はリビジョン番号付きで上書きします。
  - 共通プロンプトはアカウント単位の経路がどのみち必要なので、同じ仕組みで済みます。
  - この経路は、アカウント削除、作品の削除保管・復元、日次バックアップの対象に含めることを契約で決めます。
  - 別作品として復元したとき会話を引き継ぐかも決めます。

**F2. MCPの「依頼範囲を許可として扱う」と「モデルの主張だけで認可しない」（計画80行目と88行目）は、そのままでは両立しない**
- FUMINIWAに届くのはツール呼び出しだけで、利用者の指示は外部クライアント側にあります。範囲の情報は必ずモデルが書いた引数になります。
- 修正案: 「外部クライアントを一度だけアプリで紐付ける」ことを認可の根拠とする方針を、判断点として明記します。
  - 紐付けはクライアントごとのトークンで、ローカル接続のみとします。
  - 各呼び出しで宣言された範囲は機械的に強制し、依頼（request ID）の終了で失効させます。
  - 誤った範囲指定への安全網は、認可ではなく「変更記録＋取り消し＋履歴」と位置づけます。
  - これなら「確認を繰り返さない」とも矛盾しません。

## Medium

**F3. 「追記は一度のUndoで戻せる」「MCPの変更を取り消せる」は、標準のUndoだけでは実現できない**
- 根拠:
  - iOSのUndo履歴は話を切り替えると消去されます（`NovelKit/Sources/EditorKit/Platform/iOS/IOSTextAdapter+Editing.swift:53-54`）。
  - プロットや人物などの構造化データにはUndoの仕組みがありません（`NovelApp/Features/Plot/PlotModeView.swift:578` のみ）。
  - 現行の校正反映は、本文全体が一致するときだけ適用します（`NovelKit/Sources/EditorKit/Core/EditorCommandSession.swift:88-91`）。
- 修正案: AIによる変更の取り消しを「依頼単位の逆操作」として定義します。
  - 依頼の記録に、対象ごとの変更前後を保存します。
  - 取り消すときは同じ箇所の競合を確認します。
  - 標準Undoは「開いている話で、途中に他の操作が挟まっていない場合」の補助に限ります。

**F4. MCPが対象にできる作品が決まっていない**
- 作業画面のウィンドウは1つで、同時に開ける作品は1つです（`NovelApp/Application/FuminiwaApp.swift:174-182`）。
- 修正案: MCPは「現在開いている作品のみ」とすることを推奨します。開いていない作品を画面なしで編集する方式は、今回の対象外と明記します。

**F5. アカウント削除で、新しく作る保管データが消えない恐れがある**
- 根拠: アカウント削除（`SyncServerV2/src/account_deletion.rs:131-168`）と作品削除（`SyncServerV2/src/work_deletion.rs:32-44`）は、どちらも削除するテーブルを名前で列挙しています。
- 計画18行目は「別に扱う」とだけ書いています。
- 修正案: 次を契約に明記します。
  - アカウント削除（720時間後）の時点で、削除保管中の作品・保管データ・AI用データは1年を待たずに消去する。
  - `account_deletion_gate` のテストに、新しいテーブルが残らないことの確認を加える。

**F6. 「1年」が最低保証か上限かが決まっておらず、日次アーカイブが二重になり得る**
- 現状、スナップショット（作品の各時点の記録）は作品削除のとき以外は消えません。削除は `work_deletion.rs` のみです。
- そのため、削除していない作品については「7日間は各時点、それ以前は日単位で1年」をすでに満たしています。
- 計画29行目・35行目の独立した日次アーカイブは、データを間引かない限り復元力を増やさず、保存先が2つになるだけです。
- 修正案:
  - 1年を最低保証とする場合: アーカイブは作らず、履歴はそのまま残します。削除はフラグで隠す方式にし、1年後の消去処理と「任意の時点から別作品として取り出す」経路を作ります。
  - 上限とする場合: データを間引く方式の設計が必要です。
  - どちらの場合も、「日単位」の区切りをどのタイムゾーン（例: 日本時間）にするか決めます。

**F7. 他端末で削除された作品を、この端末で編集し続けた分が保護されない**
- 根拠:
  - server側は、削除済み作品へのすべての命令に NotFound を返します（`SyncServerV2/src/postgres.rs:2116-2125`）。
  - アプリ側は404を回復不能な失敗として扱い（`NovelKit/Sources/NovelSyncV2Runtime/ProductionSyncV2RemoteClient+HTTP.swift:401-402`）、送信を隔離して再送しません（`NovelKit/Sources/NovelSyncV2Application/SyncV2Application+Worker.swift:413-414`）。
  - 削除を他端末へ伝える仕組みもありません。
- 受入項目4（計画56行目）はこのケースを含んでいません。
- 修正案: 「他端末で削除済み」と表示し、「新しい作品として残す」を選べるようにします。仕組みは別作品復元の経路を流用します。受入項目にもこのケースを加えます。

## Low

- **F8. 自動再試行の具体策と、5分表示の対象範囲**（再試行の不足自体は計画が認識済み）
  - 通信やサーバーの一時的な失敗は、送信待ちに戻したうえで処理を終了しています（`SyncV2Application+Worker.swift:411-412`）。起動時・前面復帰時・接続回復時にだけ再開します（同 `:8-16`）。
  - 修正案: 未送信のある作品ごとに、待ち時間を段階的に延ばす（上限60秒）再試行タイマーを入れます。
  - 5分表示は送信待ちだけでなく、隔離・競合の選択待ち・アカウント不一致の状態も対象に含めます。回復不能な失敗は自動では再送されないためです。
- **F9. プロンプトの移行**
  - 現在のプロンプトは用途別・端末別に保存されています（`NovelApp/WritingAssistant/AssistantPreferences.swift:18-25`）。
  - 用途別プロンプトと共通の基本プロンプトの対応づけを決めます。
  - 端末ごとに内容が違う場合の扱いも決めます。推奨は「最初に移行した端末の内容を採用し、他端末の値は黙って捨てずに取り込み候補として残す」です。
- **F10. 実行中表示が残り続ける問題**
  - 依頼した端末が戻らないと、他端末では「実行中」のままになります。
  - 修正案: 「実行中」はその端末だけの状態にし、同期するのは「依頼」と「完了・中断などの最終状態」だけにします。他端末からは手動で「中断として閉じる」を選べるようにします。
- **F11. 同期していない作品の削除**
  - 一度も同期していない作品は、削除すると即座に完全消去されます（`NovelKit/Sources/NovelSyncV2Store/LocalSyncV2Store+Deletion.swift:36-37`、`NovelKit/Sources/NovelSyncV2Application/SyncV2Application+Deletion.swift:38-42`）。
  - これは「同期した作品のみ保護」という受け入れ済みの方針と整合します。ただし計画15行目は削除全般を「隠す操作」に変えるように読めるため、同期していない作品が対象外であることを明記します。
