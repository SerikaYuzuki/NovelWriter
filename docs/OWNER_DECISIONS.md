# 利用者が決めること

2026-09-12の文書整理で、既に決まっている製品方針と未決事項を分けた。**今回のMarkdown改訂に追加の判断は不要。** 以下は該当する実装・公開段階に進む前の判断であり、現在のiOS・保存・同期の不具合修正を止める理由にはしない。

## 1. 文書だけの変更をマージするときの検証

**決めること:** Markdownだけの変更も、アプリ・同期を含む全体検証の成功を必須にするか。

現行D-014はマージ前の`Scripts/check.sh`全通しを要求する。この改訂では作業中の検証を変更範囲に合わせたが、マージ要件は維持した。現在は文書変更と無関係なiOS認証ファイルの行数で構造Gateが失敗するため、今の規則でマージするにはその修正と全体検証も必要になる。

| 選択肢 | 影響 |
| --- | --- |
| 文書だけの変更は参照・リンク・差分確認でマージできるようにする | 通常説明の改訂がコード側の既存失敗で止まらない。wire／schemaに対応する規範変更やscriptが読む文書は、対応する検証も必要とする |
| 全てのマージで全体Gateを維持する | 現行D-014の運用を継続する。文書のみでも既存のコード失敗を解消するまでマージできない |

**推奨案（未採択）:** 文書だけの変更に限定した例外を設ける。採択するならD-014へ後続Decisionで例外を記録し、AGENTSとPR templateのマージ条件を一緒に更新する。今回のローカル文書改訂は完了できるため、回答待ちで作業は止めない。

## 2. 公開前: アカウントを失った場合の原稿の扱い

**決めること:** Appleが唯一のログイン手段で、Apple側の失効・削除が起きた場合に、FUMINIWAアカウントをどの条件で回復できるようにするか。

[AUTH 9章](AUTH.md)では、Apple identityの失効とFUMINIWA原稿の削除を分けている。端末内原稿は保持するが、オンライン原稿の回復方針は後続Product Decisionとして未決である。

| 選択肢 | 影響 |
| --- | --- |
| 同じApple identityの再認証による回復を基本とする | 通常の再認証は単純になる。元identityを回復できない場合の扱いを別途定める必要がある |
| それに加え、本人確認を伴う個別回復を提供する | 失ったidentityへの救済を増やせるが、本人確認・account付替え・運用対応を新しく設計する必要がある |

**推奨案（未採択）:** まず同じidentityでの再認証と端末内原稿のExportを確実にし、個別回復を提供するかは公開対象・運用体制に合わせて決める。別AccountIDへの原稿の暗黙移動や、未実装providerの追加で代用しない。

## 3. 公開前: 削除の取消猶予と保持期間

**決めること:** アプリからアカウント削除を求めたとき、取消できる期間、オンライン原稿が消える時点、backupから消える期限をどうするか。

現行契約にはaccount lifecycleの公開Gateがあるが、期間は決定されていない。サインアウト、Apple連携失効、アカウント削除、端末内原稿の削除を別の操作として説明する必要がある。

| 選択肢 | 影響 |
| --- | --- |
| 短い取消猶予を設けてから削除を確定 | 誤操作を救済できる。猶予中の接続・同期・取消の状態を実装する必要がある |
| 削除要求を即時確定する | 取消の状態は減るが、誤操作で回復できなくなる。backup消去とApple revokeの完了はなお別途追跡が必要 |

**推奨案（未採択）:** 取消猶予を設け、原稿本体とbackupの期限を明示する。具体的な日数はここで仮決定しない。選択後にversioned lifecycle契約、UI、durable retry、Apple token revoke、remote削除完了のread-backを一緒に設計する。[AUTH](AUTH.md)、[公開技術Gate](COMMERCIALIZATION_IMPLEMENTATION.md)が根拠。

## 4. Windowsに着手するとき

**その時点で決めること:** 最低対応Windowsと配布方式。本文editorの制約により既定の執筆機能を変える必要がある場合は、その取捨選択。

WinUI 3 + C# / .NETを使い、package・同期契約とfixtureを共有する方針自体はD-036で採択済み。現時点はW0未完了である。SDKの具体版とeditorの技術選定は、着手時に最新の公式仕様と日本語IME / Undoの試作結果に基づいて実装側で進める。既定要件を満たす通常の選定に逐次承認は求めない。今回の文書整理では新たな技術選定をしていない。[CROSS_PLATFORM 5章](CROSS_PLATFORM.md)参照。

## 判断の取り直しが不要なこと

以下は既定方針の実装・検証で進められる。

- iOSの主要機能階層、執筆補助、promptコピー、製品向け履歴UIをv2へ接続すること。
- 認証済み新規作品の同期不具合、D-076構造Gate、notification route等の契約不一致を直すこと。
- local-first、SQLite v2、Apple-only、server-readable、clipboard-onlyという採択済みの境界。
- 文書を短い入口と必要時の詳細参照へ整理し、過去の決定・証拠を保持すること。

既定機能の削減、公開方針や優先順位の変更、provider統合の再開を提案する場合は、新しい判断として具体化する。

## 判断と別に、利用者の協力が必要な確認

署名済みMac / iPhoneのApple認証・信頼設定・実機UI受入は、準備が整った時点で操作を依頼する。[v2引き継ぎの受入基準](SNAPSHOT_SYNC_V2_HANDOFF.md)を使い、結果を記録する。これは既決仕様を再承認してもらう手続きではない。

GitHub反映、デプロイ、旧データ削除は、それぞれの実施依頼と具体的対象があるときに行う。今回の文書改訂には含めていない。
